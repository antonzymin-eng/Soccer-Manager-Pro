## 1. Decision: FR-TS-011 is an internal-consistency correction

### Defect

FR-TS-011 currently says every CI pipeline includes the complete Spec #16 §5 regression tiers. That conflicts with the already-published Pipeline-to-Gate Map in §6.2.4:

- pre-commit: no determinism gate;
- PR: `Partial (#16 unit tier)`;
- nightly: `#16 §5 full suite`.

The correction is therefore justified first by the spec's own internal inconsistency, not by runner scarcity or implementation convenience.

### Candidate catalogue statement

> **FR-TS-011 — MUST.** Each CI pipeline MUST execute the determinism scope assigned to it by §6.2.4 in Spec #16 canonical order: pre-commit = none, PR = #16 unit tier, nightly = complete #16 §5 suite on the pinned certified host.

This keeps §2.2 as a single-modality rule statement. Mechanics belong in §3.2.2 and verification belongs in §5.7 / §5.6.

### Mechanics to land atomically

§3.2.2 must state that §6.2.4 owns the per-pipeline scope, canonical order applies wherever multiple #16 tiers execute, PR evidence is non-certifying, and authoritative certification requires a successful complete #16 §5 run on the pinned certified host. §5.7 must verify the same contract; §5.6 must name the actual artifact/mechanism rather than restating a different scope.

## 2. Decision: FR-TS-062 is inactive until Stage 1 flake tooling

### H2 resolution

The current repository does **not** double-run every test in ordinary CI, and §5.2 already publishes FR-TS-061…067 as inactive pending the §7.2 flake integration layer. §7.2 places quarantine/eviction tooling in **Stage 1**. Therefore the earlier A3.4 rationale that FR-TS-062 currently doubles ordinary CI cost was false and is withdrawn.

The merits case is instead:

1. the future rule should have one explicit required lane rather than an optional `or explicitly requested` path that may never execute;
2. automatic quarantine after a single disagreement is too strong a disposition for one observation; and
3. quarantine boundaries are already owned by FR-TS-063/077/094 and should not be duplicated in FR-TS-062.

### Activation reconciliation

The flake partition must stop publishing tooling-dependent rules as Stage 0+1 while §7.2 assigns their machinery to Stage 1. The atomic patch should split the band as follows:

- FR-TS-061 (definition): Stage 0+1;
- FR-TS-062 (repeated-execution detection lane): **Stage 1**, activated when the §7.2 flake-detection lane is implemented;
- FR-TS-063…066 (quarantine/expiry/eviction mechanics): **Stage 1**, activated with §7.2 flake quarantine/eviction tooling;
- FR-TS-067 (retry/sleep anti-pattern ban): Stage 0+1.

This removes the reached-but-unmet-MUST ambiguity rather than hiding it behind a criterion.

### Candidate catalogue statement

> **FR-TS-062 — MUST.** Once Stage 1 flake tooling activates under §7.2, the dedicated nightly flake-detection lane MUST compare repeated executions of the same revision under the same `EnvironmentFingerprint` and record every disagreement for §3.7 disposition.

The row contains one modality. It does not republish FR-TS-077's quarantine boundary.

### Mechanics to land atomically

§3.7.2 should require the dedicated nightly lane to execute the eligible test set twice on the same revision/fingerprint, record both outcomes, and route disagreement to §3.7.3 for disposition. A targeted diagnostic rerun may supplement investigation but does not substitute for the required nightly lane. Quarantine is not automatic on the first disagreement; §3.7.3 owns that decision. §5.2 and §5.6 must reproduce the revised activation stages exactly.

## 3. Decision: Code Standards KD-4 modernization

### Defect

KD-4 still states that Stage 0 verification is manual and no static-analysis tooling is required, justified by the historical claim that no source code exists. The repository now contains source code and automated checks. The historical rationale belongs to the drafting history; it is not a valid current verification rule.

### Candidate KD-4

> **KD-4 — Verification becomes automated when the rule is mechanically decidable.**  
> **Statement:** Manual review remains required for semantic judgments that current tooling cannot decide reliably. Once source code and a mechanically reliable checker exist for a Code Standards rule, the applicable automated check participates in conformance according to Spec #19 / repository-gate policy. Architecture assertions that require A4 compiler-closed discovery or later proof mechanics remain non-blocking until their explicit activation prerequisites are satisfied.  
> **Rationale:** Initial Stage 0 drafting had no source corpus, so manual review was the only meaningful mechanism. That historical premise has expired. Numeric lint-threshold deferral remains a separate KD-5/D1 concern.  
> **Consequence if violated:** Either implemented reliable checks are treated as optional, or immature tooling is granted authority over claims it cannot prove.
