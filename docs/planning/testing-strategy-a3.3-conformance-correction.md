## Why this correction exists

Integration-plan v0.38 is a September 3 checkpoint. Its version-history row correctly recorded the repository state at that time: D2/D3 were deferred and the FR-TS-075/079 pre-commit/nightly/local-runner gap was open. Those statements are no longer the current candidate implementation state after PR #357. This correction preserves v0.38 as history while providing the current A3 hand-off state instead of silently rewriting what that earlier checkpoint observed.

## Current candidate state

- **D2 resolved:** FsCheck.NUnit 2.16.6 is pinned through `Directory.Build.targets`.
- **D3 collector resolved:** coverlet.collector 6.0.4 and `tools/dotnet-ci/coverage.runsettings` are wired. The §5.5 per-tier threshold mapper/auditor is still a separate open implementation obligation; D3 is not used to claim that mapper exists.
- **FR-TS-079 local/CI composition implemented:** `tools/run-tests-local.sh` is the stable composition entry point and PR CI reuses `--pr` rather than directly calling the lower-level Linux gate.
- **Pre-commit topology corrected:** the hook evaluates the staged Git index through a persistent snapshot under `.git/testing-strategy`. Bootstrap performs the one-time full materialization outside the normal 60-second acceptance measurement. Later hook runs compare the recorded Git index tree with the current tree, remove deleted tracked paths with a linear manifest `comm`, and refresh only changed index paths. Unchanged tracked files retain their mtimes and untracked generated/bin/obj outputs survive, so MSBuild can actually reuse incremental state. Generated `.gen.csproj` and solution files are also written only when their bytes change, so the generator does not invalidate the cache by touching project files. Snapshot materialization disables both Git-LFS process/smudge execution locally and sets `GIT_LFS_SKIP_SMUDGE=1`; the staged pointer bytes are sufficient for this test gate, so an offline or intentionally un-fetched LFS object cannot reject a commit before tests run. The normal attempt remains hard-bounded to 60 seconds.
- **Pre-commit selection corrected:** `tools/dotnet-ci/precommit.runsettings` uses anchored NUnit METHOD-name prefixes for `int_`, `sim_`, and `e2e_`. Bare `FullyQualifiedName` substring exclusions are not used; names such as `Point_`, `Fingerprint_`, `MalformedInt_`, and `QuickSim_` remain eligible.
- **Nightly topology implemented without pretending runner availability:** GitHub-hosted Linux supplies non-certifying functional/simulation/soak evidence. The authoritative Spec #16 §5 self-hosted Windows/Unity job is gated by repository variable `DETERMINISM_CERTIFIED_RUNNER_ENABLED=true`; until a certified runner is actually registered/configured, a GitHub-hosted notice records the open operational condition rather than queueing the unavailable job.
- **Owner-held RED handling corrected:** `sim_match_engine_close_chance` is neither quarantine nor silently ignored. The low-level gate selects/excludes it by exact test `Name`; its ledger records diagnostic expectations as named fields (`meanCosine=-0.165`, `goalwardShare=0.407`). The verifier requires one unambiguous result and one unambiguous exact assignment for each named field, no extra returned results, the expected failed outcome, and the expected test-failure runner exit. A drifted current value cannot pass merely because an assertion message also prints the historical baseline. Unexpected green/drift/ambiguity/abnormal execution blocks.
- **Auditors implemented without a retroactive merge landmine:** routine pre-commit/PR/nightly composition runs checklist and §5 schema auditors in survey-only mode. `SPEC_INDEX.md` is the canonical approval authority. PR CI receives the PR base SHA, compares base/head registry states, and reruns both auditors as blocking only for spec directories whose canonical registry status changes from non-approved/missing to `APPROVED` or whose approval metadata signals an explicit reapproval. Missing base history, an unreadable/unparseable registry, or a registry folder that does not resolve to a real spec directory in the candidate head fails closed. The blocking approval walk is invoked by `tools/run-testing-strategy-approval-audit.sh` inside the repository's **required `Spec hygiene checks` context**; the non-required Linux functional job also exercises the same policy path, but merge safety no longer depends on that optional context.
- **Checklist auditor contract is intentionally structural and mechanically decidable:** Stage 0+1 automation verifies that checklist artifacts/rows exist, Markdown approval checkboxes are checked, repository file paths resolve, cited Markdown sections actually exist, and explicit programmatic invocations have successful captured output. Only an explicit backticked invocation such as `python3 tools/check.py` is executable evidence; a `.cs`, `.py`, `.sh`, or other source-file citation by itself remains file evidence and does not demand captured execution. The required approval helper invokes explicit checks without a shell and captures their stdout/stderr; command parsing excludes inline `python -c`/`-m`, mutating Git subcommands, and other unbounded command forms.
- **Natural-language semantic entailment is not claimed by the automated checklist auditor:** Testing Strategy §3.5.2 already assigns a Stage 0 reviewer to walk each checklist citation against current repository state. That reviewer remains responsible for deciding whether a cited file/section actually supports the checklist claim, including negation, polarity, units, and prose meaning. Earlier PR #357 revisions tried to automate that judgment with token/quorum heuristics; repeated tightening alternated between fail-open contradictions and fail-closed legitimate citations. Those heuristics are removed rather than treated as proof. This is a scope correction of the Stage 0+1 implementation, not a relaxation of KD-6: FR-TS-040's “containing the claimed value” obligation still exists and must be discharged by the Stage 0 review unless a programmatic check proves the fact.
- **§5 schema auditing remains structural:** an enforced approval scope must contain an auditable checklist and §5 test plan; §5.6 links must resolve to actual §9 checklist rows; and Appendix C §5.1 requires all five taxonomy rows, including Determinism and End-to-end / soak.
- **Survey debt must be remeasured under the corrected contract:** the earlier **548 findings** (219 checklist + 329 §5 schema) on `edf6d4b` came from an intermediate auditor whose semantic-token behavior has now been removed. It is historical evidence of substantial documentation debt, not a comparable current count. A3.4 must measure structural findings under the final contract and separately record the Stage 0 manual semantic-review burden.
- **Required-status state checked:** the live `CI for Main branch` ruleset does not require either the historical or candidate Linux functional-gate context. The six required contexts remain Markdown lint, YAML lint, Markdown link check, Spec hygiene checks, File manifest sanity, and C# format check. Approval-transition enforcement runs inside required `Spec hygiene checks`, while the long Linux functional job remains non-required evidence. The functional-job rename therefore does not create an unreachable required status.

## A3.4 acceptance rule

A3.4 must evaluate executable state, normative merit, structural corpus debt, Stage 0 semantic review, and recorded execution evidence separately. A versioned script, timeout, cache design, workflow YAML, runner label, or repository variable proves topology/configuration only. A resolved file/section proves citation structure only; it does not prove natural-language entailment. Likewise, implementation state does not justify relaxing an existing MUST. Spec #19 may be reapproved only after the operational facts are recorded, structural auditor debt is dispositioned, the required manual KD-6 citation review is recorded, and FR-TS-011/062 are accepted or rejected on their merits.
