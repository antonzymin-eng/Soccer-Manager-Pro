## FAIL Findings

### FAIL-1 — A-06 + T-03 — Decision Tree #8 §3.2: Wrong Coordinate System Origin [HIGH]

**File:** `docs/specs/decision-tree/section-3-2.md:308`

**Finding:** The `PitchGeometry` pseudocode class claims:
```
/// Coordinate system (consistent with Ball Physics #1 §2.2 and Agent Movement #2 §2.1):
///   Origin (0, 0) = centre of pitch
///   X-axis: pitch length (−52.5m to +52.5m; total 105m)
///   Y-axis: pitch width (−34m to +34m; total 68m)
```

This is a centered origin. The authoritative coordinate system (Ball Physics #1 §1.2 per CLAUDE.md) is corner-origin:
- **Correct:** Origin at corner (0, 0, 0); X: 0–105m; Y: 0–68m
- **DT §3.2 actual:** Origin at pitch center; X: −52.5 to +52.5m; Y: −34 to +34m

Downstream consequence: every hardcoded position in the class is wrong in corner-origin space:
| Constant | DT §3.2 value | Correct corner-origin value |
|----------|---------------|----------------------------|
| `HOME_OPPONENT_GOAL_CENTRE` | `(52.5, 0)` | `(105, 34, 0)` |
| `HOME_OWN_GOAL_CENTRE` | `(-52.5, 0)` | `(0, 34, 0)` |
| Goal posts L/R | `(±52.5, ±3.66)` | `(105/0, 34±3.66, 0)` |

The citation "consistent with Ball Physics #1 §2.2" is also wrong — the authoritative section per CLAUDE.md is §1.2, not §2.2. Ball Physics §3.1.md confirms corner-origin (verified: "Origin (0,0,0): Corner flag at home team's left defensive corner; Away goal: X=105m, centered at Y=34m").

**Probe trigger:** A-06 FAIL (direct origin claim "Origin (0, 0) = centre of pitch"). Secondary: T-03 (inverted domain convention — coordinate origin).

**Required fix:** Rewrite `PitchGeometry` class to use corner-origin coordinate system. Update all position constants. Correct the citation from "§2.2" to "§1.2 and Appendix C". Append version-history entry to `section-3-2.md`.

### FAIL-3 — A-04 + T-08 — Domain Tag Registry (#16 §3.4): Silent Gaps at `0x18` and `0x1C` [MEDIUM]

**File:** `docs/specs/deterministic-sim/section-3.md` §3.4

**Finding:** The allocated domain tag sequence is:
```
0x10 DOMAIN_TAG_PHASE
0x11 DOMAIN_TAG_SNAPSHOT_PAYLOAD
0x12 DOMAIN_TAG_SNAPSHOT_HEADER
0x13 DOMAIN_TAG_RNGDRAW
0x14 DOMAIN_TAG_ENV_FP
0x15 DOMAIN_TAG_EVENT_LEDGER
0x16 DOMAIN_TAG_HEADING
0x17 DOMAIN_TAG_POSITIONING_AI
0x18 ← MISSING (no row; was mentioned as "reserved for #11 GK" in v1.0.3 changelog before GK shifted to 0x1D)
0x19 DOMAIN_TAG_PRESSING_AI
0x1A DOMAIN_TAG_DEFENSIVE_AI
0x1B DOMAIN_TAG_ATTACKING_AI
0x1C ← MISSING (no row; within the declared "Phase B/C block 0x17…0x1C" but never filled)
0x1D DOMAIN_TAG_GOALKEEPER
```

Per A-04 criterion: "every gap in the allocation sequence has an explicit `_RESERVED_0xNN_` placeholder row in the §3.4 table." Neither `0x18` nor `0x1C` has a placeholder row. `0x18` is documented only in a changelog entry (v1.0.3) as an abandoned reservation — it is not handled in the live §3.4 table. `0x1C` is undocumented entirely.

A developer adding a new subsystem domain tag would see `0x1D` as the last entry and assume the next available value is `0x1E`, unaware that `0x18` and `0x1C` are orphaned values that cannot be reused without a coordination process.

**Probe trigger:** A-04 FAIL (silent gap without placeholder row). Secondary: T-08 (DOMAIN_TAG gaps).

**Required fix:** Add two `_RESERVED_0xNN_` placeholder rows to the §3.4 domain-tag table:
- `| _RESERVED_0x18_ | 0x18 | — | Skipped: originally informally reserved for Goalkeeper Mechanics #11 (ERR-011-001 v1.0.3 note) before GK was reallocated to 0x1D. Must not be reassigned without explicit ERR tracking. |`
- `| _RESERVED_0x1C_ | 0x1C | — | Skipped: within the ERR-012-001 Phase B/C block (0x17–0x1C); block closed at 0x1B. Must not be reassigned without explicit ERR tracking. |`

## WARN Findings

### WARN-1 — A-12 + T-14 — Collision System §6: Performance Budget ms-Literals Match Tick-Rate Pattern [LOW]

**File:** `docs/specs/collision-system/section-6.md` (multiple lines)

**Finding:** A-12 scans for `\d+(\.\d+)?\s?ms` literals and requires each to be in the whitelist `{10 Hz, 60 Hz, 100 ms, 16.67 ms, 16.7 ms, 17 ms}`. Collision System §6 contains performance budget figures (`~0.18ms`, `<0.15ms`, `<0.3ms`, `<0.5ms`, `0.1ms`, `0.3ms`, etc.) that match the regex but are performance estimates, not loop-rate declarations.

These are likely intentional and correct (they are §6 performance analysis), but the A-12 probe as mechanically specified would flag all of them. Human review confirms none are loop-rate literals. Recommend adding a `## Performance Budget` section exemption to A-12 when the probe scripts are implemented.

**Action:** Human triage confirms NO ACTION needed on spec content; A-12 implementation should add a `section-6` carve-out for performance-budget context.
